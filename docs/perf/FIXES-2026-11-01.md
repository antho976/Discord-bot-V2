# Performance fixes, 2026-11-01

Same machine as [BASELINE-2026-11-01](BASELINE-2026-11-01.md): AMD Ryzen 7 9800X3D (16 threads),
CachyOS, `--release` (opt-level "s", thin LTO). Render's instance is far smaller and shared, so
read the times as relative.

## `/level top`: pressing Next or Previous

The owner said "it just takes a while to go to a next page" and suggested caching the first
three or four pages, refreshed every 30 minutes, if that would be much better.

**What a page change was:** acknowledge the click (defer, one Discord round trip), *then*
download ten faces (each up to 3 s, 4 s for all), *then* draw the PNG, then upload it to
Discord, then the client loads the image from Discord's CDN. Only the middle steps are ours.

`cargo run --release -p feat-levels --example board_cost` (30 runs; `FACES=64` for the face
downloads, which need the network):

| Step | Before | After |
|---|---:|---:|
| Ten faces, first time | 46-98 ms (3 runs, 128 px) | 45-70 ms (3 runs, 64 px) |
| Ten faces, seen in the last 30 min | 33-53 ms (fetched again) | 0 ms (kept) |
| Draw the PNG (10 rows, 10 faces) | 46 ms p50, 48 ms p95 | unchanged |
| PNG size | 135 KB | unchanged |
| Order | defer, then faces + draw | faces + draw *while* the defer is in flight |

The next page's faces are also fetched in the background after each page is shown, so a Next
press usually finds them kept.

**Why not cache whole pages:** a cached page would save the faces and the 46 ms draw, about
100-150 ms here, but it would show XP up to 30 minutes old and couldn't pick out the member who
pressed the button. Keeping faces and drawing during the defer saves about the same time
(one Discord round trip plus the face downloads) with live numbers.

**Not measured:** the Discord side (defer round trip, the upload, the client loading the
image), which needs a live bot; and the times on Render's smaller CPU, where the 46 ms draw
will be several times longer.
