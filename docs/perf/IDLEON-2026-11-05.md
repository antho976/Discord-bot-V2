# Idleon account check: baseline, 2026-11-05

Journey: a member submits their save on `/p/{guild}/idleon` and gets the review page.
Before any optimizing; the owner wants it to cost as little as possible once public.

Machine: AMD Ryzen 7 9800X3D (16 threads), release build (`bot preview`), localhost.
The production box, server1, is an Intel i5-8500T (6 cores, 16 GB): expect roughly 2x the
CPU time per review there (estimate from single-thread ratings, not measured).
Data: 40 real current saves (IdleonToolbox copies, World 7), 1.75 MB each URL-encoded.
Client: `load2.py` (closed loop, one process per concurrent client), 12 s per step.

| At once | Reviews/s | p50 | p95 | Bot CPU |
|---|---|---|---|---|
| 1 | 69 | 14 ms | 15 ms | 0.94 cores |
| 2 | 137 | 14 ms | 15 ms | 1.88 cores |
| 4 | 142 | 27 ms | 28 ms | 1.94 cores |
| 8 | 142 | 53 ms | 72 ms | 1.97 cores |
| 16 | 134 | 107 ms | 148 ms | 1.96 cores |

- CPU per review: about 13.6 ms (0.94 cores / 69 per s), all of it in the request: parse the
  paste, 112 checks (about 6 ms, `examples/review.rs`), render and gzip the page (92 KiB
  gzipped, about 1 MB raw).
- Throughput stops at about 2 cores: requests beyond that queue. Nobody was ever told to retry
  (the 4-at-once limit never filled, since each review holds a runtime thread to the end).
- Memory (RSS): 23 MB idle, 28 MB after the form, 40 MB after one review, 50 MB after six,
  144 MB peak under 16 at once. The allocator keeps what a review freed, so the feature costs
  about 25 MB from its first use until a restart.
- Binary: 30 MB (game data 684 KiB and 2,757 pictures, 3.4 MB, built in).

Open for the optimizing pass: memory kept after a review (the paste and the parsed save as
`serde_json::Value`, a 1 MB page), CPU per review, and the review holding a runtime thread
(move it to `spawn_blocking` so other pages never wait behind it).
