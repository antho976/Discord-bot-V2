# Idleon account check: lighter checks, 2026-11-06

Same harness as IDLEON-2026-11-05.md (`docs/perf/idleon/`), release build, `bot preview`,
AMD Ryzen 7 9800X3D, 40-63 real World 7 saves. Since that baseline the page grew "what to do"
for 112 mechanics, so "before" here is re-measured on that page.

| | Before | After |
|---|---|---|
| CPU per check | 20.2 ms | **13.6 ms** |
| Checks per second, one at a time | 47 | **72** |
| Page sent (raw / gzip) | 1.30 MB / 147 KB | **564 KB / 132 KB** |
| RSS after 2 checks / 22 checks | 43 / 53 MB | **35 / 34 MB** |
| RSS after the load test | 45-65 MB | **46 MB** |
| Another page while 8 checks run, p50 / p95 | 19.3 / 31.7 ms | **0.4 / 0.6 ms** |
| Peak RSS, 8 at once | 71 MB | 83-86 MB (see below) |

What changed, each measured on its own:

1. **Show all lists as data** (73% of the page was those lists): drawn by the page script when a
   list opens. Page 1.30 MB to 564 KB; CPU per check unchanged (building them wasn't the cost).
2. **The paste as plain text** (`enctype="text/plain"`): profiling showed ~18% of the server's
   time in percent-decoding a URL-encoded paste (a 0.7 MB save arrives as 1.75 MB). CPU per check
   20.2 to 13.6 ms.
3. **Freed memory handed back** (`malloc_trim`) once, 2 s after the last check of a burst. After
   every check it cost ~1.2 ms a check; debounced it costs nothing during a burst. RSS after
   checks 50 to 35 MB.
4. **Checks off the runtime threads** (`spawn_blocking`, at most 2 at once, others wait up to
   10 s): other pages and Discord events no longer queue behind checks. Peak RSS during a burst
   is ~12 MB higher (the blocking threads' malloc arenas); it is handed back after the burst.

Profile after (flat, `perf record` on a symbol build): malloc/free ~25% (serde_json `Value`
for the save and the game data), gzip ~8%, JSON parse ~10%. Not done, with why:

- Game data stays a `serde_json::Value` (7.7 MB resident after the first check, 5 ms to load):
  typed tables would halve it but every check reads `GAME.rows`; not worth it now.
- Call-graph profiling is refused on this machine (`perf_event_paranoid` 2), so attribution is
  flat (by function), not by caller.
